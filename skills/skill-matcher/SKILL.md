# 역량 매칭 리포트

이력서와 채용공고를 대조해 **지원 판단에 필요한 답**을 줍니다.
"잘 맞습니다" 같은 말은 하지 않습니다. **어떤 항목이 왜 맞고 왜 안 맞는지**를 근거와 함께 냅니다.

## 입력

둘 다 필요합니다. 형식은 아무거나 받습니다.

- **원문 방식**: 이력서 텍스트 + 채용공고 텍스트 → 이 스킬이 추출까지 직접 수행
- **JSON 방식**: [이력서 역량 추출기] · [채용공고 요구역량 분해기] 의 JSON 출력을 그대로 붙여넣기 → 추출 단계를 건너뛰고 매칭만 수행

한쪽만 JSON이어도 됩니다.

## 처리 절차

### 0단계 — 추출 (원문 입력일 때만)

이력서 → 보유 스킬 목록, 공고 → 요구역량 목록으로 각각 분해합니다.
분류 체계와 레벨 기준은 아래와 같습니다. (두 추출 스킬과 동일)

**카테고리**: `TECH` 기술·도구 / `DOMAIN` 도메인지식 / `TASK` 직무수행능력 / `SOFT` 대인·태도 / `CERT` 자격·어학 / `COND` 정량조건

**레벨**: 1 노출 · 2 보조 · 3 독립수행 · 4 개선·최적화 · 5 설계·주도

이력서 스킬에는 `recency`(current/recent/past), 공고 요구역량에는 `requirement`(must/nice/implicit)와 `priority`(1~3)를 붙입니다.
모든 항목에 **원문 인용 근거**를 답니다.

### 1단계 — 대응 찾기

공고 요구역량 **하나하나에 대해** 이력서에서 가장 가까운 보유 스킬을 찾습니다.

**표기가 달라도 같은 것은 붙입니다.** 이게 이 스킬의 핵심입니다.

| 공고 표현 | 이력서 표현 | 판정 |
|---|---|---|
| ETL 경험자 | Python으로 배치 파이프라인 구축 | ✅ 동일 (구현 수단이 다를 뿐) |
| 데이터 기반 의사결정 | A/B 테스트 설계 및 지표 해석 | ✅ 동일 |
| 커뮤니케이션 능력 | 유관부서 요구사항 정의 및 조율 | ✅ 동일 |
| RDBMS | MySQL 운영 | ✅ 상위-하위 (보유가 구체) |
| Kubernetes | Docker 사용 | ❌ 다름 (인접하나 별개) |
| AWS | GCP 운영 | ⚠️ 부분 (클라우드 개념 전이 가능, 별도 표시) |

붙일 때는 **왜 같다고 봤는지** 한 줄로 남깁니다. 근거 없는 연결은 하지 않습니다.

### 2단계 — 항목별 판정

| 상태 | 조건 |
|---|---|
| ✅ **충족** | 보유 레벨 ≥ 요구 레벨 |
| 🟡 **부분충족** | 보유 레벨이 요구보다 1 낮음 / 인접 스킬로 대체 가능 / `recency: past` |
| 🔴 **미충족** | 보유 레벨이 2 이상 낮음, 또는 해당 스킬 없음 |
| 🔵 **초과** | 보유 레벨이 요구보다 2 이상 높음 (오버스펙 신호) |

### 3단계 — 적합도 계산

**항목 가중치**

| 구분 | 강조도 | 가중치 |
|---|---|---|
| must | 1 | 5 |
| must | 2 | 4 |
| must | 3 | 3 |
| nice | – | 2 |
| implicit | – | 1 |

**충족률**: 충족 `1.0` · 부분충족 `0.6` · 미충족 `0` · 초과 `1.0`
**보정**: 이력서 스킬이 `recency: past`면 해당 항목 충족률 × `0.8`

```
적합도(%) = Σ(가중치 × 충족률) ÷ Σ(가중치) × 100
```

**계산 과정을 출력에 표로 보여줍니다.** 점수만 던지지 않습니다.

### 4단계 — 종합 판정

| 판정 | 조건 |
|---|---|
| **지원 권장** | 적합도 70% 이상 **그리고** must 미충족 0건 |
| **조건부 지원** | 적합도 50~69%, 또는 must 미충족이 있으나 우회 근거 존재 |
| **보완 후 지원** | 적합도 50% 미만, 또는 강조도 1의 must 미충족 |

must 항목이 하나라도 🔴이면 적합도가 높아도 **반드시 별도 경고**합니다. 평균에 묻히면 안 됩니다.

### 5단계 — 실행 가능한 산출물

판정만으로는 부족합니다. 지원자가 **오늘 바로 쓸 것**을 냅니다.

1. **강조할 문장** — 충족·초과 항목 중 강조도 1~2인 것을 골라, 이력서 원문을 공고 어휘로 다시 쓴 문장 3~5개
2. **보완 전략** — 🔴 항목별로: 우회 근거로 방어할지 / 단기 습득 가능한지 / 포기할지
3. **예상 질문** — 미스매칭 지점에서 나올 면접·서류 질문과 대응 방향

## 출력 형식

### ① 판정

> ## {지원 권장 / 조건부 지원 / 보완 후 지원} — 적합도 **{N}%**
> **{직무}** · 필수요건 {충족}/{전체} 충족
> ⚠️ (must 미충족이 있으면 여기에 항목명과 함께 경고)
>
> 세 줄 요약: 무엇이 강점이고, 무엇이 결정적 공백이고, 그래서 어떻게 할 것인가.

### ② 매칭 표 (미충족 → 부분충족 → 충족 순. 문제부터 보여줍니다)

| 상태 | 요구역량 | 구분 | 요구/보유 | 대응된 내 경력 | 판정 근거 |
|---|---|---|---|---|---|
| 🔴 | Kubernetes | must(1) | 3 / – | 없음 | Docker 경험은 있으나 오케스트레이션 근거 없음 |
| ✅ | Python | must(1) | 4 / 4 | "배치 파이프라인 설계, 6h→40m" | 수치 개선 근거로 레벨4 인정 |

### ③ 점수 계산

| 요구역량 | 가중치 | 충족률 | 보정 | 기여 |
|---|---|---|---|---|
| … | 5 | 1.0 | – | 5.0 |
| **합계** | **{Σ가중치}** | | | **{Σ기여}** → **{N}%** |

### ④ 강조할 문장

| # | 공고의 이 요구에 대해 | 이렇게 쓰세요 |
|---|---|---|

### ⑤ 보완 전략

| 부족 항목 | 대응 | 구체적 액션 |
|---|---|---|
| Kubernetes | 우회 방어 | Docker 기반 배포 경험을 컨테이너 이해도로 제시 + 학습 계획 언급 |

### ⑥ 예상 질문

| 질문 | 나오는 이유 | 대응 방향 |
|---|---|---|

## 반드시 지킬 규칙

1. **없는 경력을 만들지 않습니다.** 보완 전략은 "이렇게 표현하라"이지 "이렇게 지어내라"가 아닙니다. 이력서에 근거가 없으면 🔴로 두고 우회 방법을 제시합니다.
2. **모든 대응 연결에 근거를 답니다.** ETL과 파이프라인을 같다고 봤으면 왜 같은지 씁니다. 이유 없는 연결은 점수를 부풀립니다.
3. **must 미충족은 숨기지 않습니다.** 총점이 높아도 별도 경고합니다. 지원자가 헛수고하는 게 더 큰 손해입니다.
4. **점수 근거를 공개합니다.** 계산 표 없이 "78%"만 내면 신뢰할 수 없는 숫자입니다.
5. **지원 여부를 대신 결정하지 않습니다.** 판단 재료를 주고 결정은 사용자가 합니다. "지원하지 마세요"가 아니라 "이 항목이 막혀 있습니다"로 씁니다.
6. **사람을 평가하지 않습니다.** 역량과 요구의 대조만 합니다. 인성·태도에 대한 추측 금지.
7. **개인정보를 출력하지 않습니다.** 이름·연락처·주소·생년월일은 리포트에 넣지 않습니다.
